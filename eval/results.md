# Benchmark results

> **Run mode: deterministic-only.** Stage 1 is the whole pipeline here. The router, Tavily and the explanation stage are not exercised, so *checks with zero model calls* is trivially 100% and *cost per check* is trivially $0. Neither number means anything until the run goes through the router. Read them as placeholders, not results.

Generated by `uv run python -m eval.runner`. Every case carries the registry metadata it needs, so the run is offline and a rerun gives the same numbers.

- Clocks: each case is judged against its own `verified_at`. 94 of 150 carry one; the rest fall back to `2026-10-26T12:00:00+00:00`. Range `2026-10-26T12:00:00+00:00` .. `2026-10-27T13:21:37.670756+00:00`. Re-verifying one case never moves another.
- Ecosystems covered: docker, huggingface, pypi.
- Cases: **150** | passed: **145**

## Known limits

- Floating base tags (e.g. `python:3.12-slim`) go to REVIEW by design: a tag without a patch release cannot be shown to meet its floor (`check_unavailable`, rule P10).
- 2 of 30 generated names were registered on PyPI within the last 3 months; removed from the set.

## What these numbers do not show

**56 of 150 cases have registry facts that were never confirmed against a live source.** The dates, versions and hashes in them are written by `eval.make_cases` or presumed by `eval.fetch_osv_malicious`, not read from PyPI. Run `eval.verify_labels` to replace them; until then these are figures about fixtures, not about packages.

**25 malicious cases describe a package as it was before the registry removed it.** Those facts are a simulation, written so that P2 (`osv_malicious`) is the rule under test instead of P1 (`not_found`). The advisory ids are real; the registry state is not. Recall on this group says the OSV path is wired up, not that it caught anything in the wild.
